## Теория

Интерфейс — способ взаимодействия, а не только цвета и кнопки. Консоль, Telegram и настольное окно должны отвечать на три вопроса: что можно сделать, какие данные нужны и что получилось.

### Начинаем с цели

Для записи на услугу цель — получить подтверждённое время, а не заполнить как можно больше полей. Запишите путь: выбрать услугу → дату → время → проверить → подтвердить. Каждый шаг содержит одно понятное действие.

### Ввод соответствует данным

| Данные | Средство |
|---|---|
| Произвольное название | Текст с ограничением длины |
| Один вариант из нескольких | Кнопки/список |
| Несколько независимых признаков | Отдельные переключения |
| Число | Текст с проверкой формата и диапазона |
| Подтверждение операции | Явная кнопка с результатом действия |

В Telegram Reply-кнопка отправляет текст, Inline-кнопка — callback. Не выбирайте элемент только потому, что он выглядит интересно.

### Состояние должно быть видно

Нужно различать пустой каталог, ожидание данных, успешное сохранение и ошибку сервиса. Сообщение «Что-то пошло не так» без дальнейшего действия редко помогает. «Не удалось загрузить список. Попробуйте ещё раз» даёт следующий шаг.

### Предотвращение ошибок

Не требуйте помнить ID, если можно выбрать запись из списка. Показывайте выбранные значения перед подтверждением. При ошибке оставляйте уже введённые допустимые данные. Отмена должна быть доступна и иметь предсказуемый результат.

### Подписи и обратная связь

Кнопка «Удалить запись» понятнее «ОК». Значение не стоит передавать только цветом или эмодзи — добавьте текст. Одинаковые действия называются одинаково. Для долгой операции сообщите об ожидании, но не показывайте заранее ложный успех.

### Проверка сценария

Дайте схему человеку, который её не создавал. Попросите оформить одну запись и объяснить, что он ожидает после кнопки. Место, где приходится гадать, указывает на проблему перехода или подписи, а не на недостаток инструкции.

## Частые ошибки

Не считайте красивый экран доказательством понятного пути. Не заставляйте вводить одно и то же после любой ошибки. Не ограничивайте результат цветом.

## Разбор практических задач

Сначала запишите свой план и ожидаемый результат, затем сравните с разбором.

### Задача 1. Подпись действия

#### Условие

Уточните неопределённые кнопки.

#### Как рассуждать и алгоритм

Название должно описывать эффект, а не внутреннюю команду программы.

#### Решение

```text
«ОК» → «Сохранить заявку»
«Назад» → «К выбору даты», если назначение иначе неочевидно
«Повтор» → «Повторить поиск»
```

#### Проверка

По подписи можно предсказать следующий результат.

### Задача 2. Пустое состояние

#### Условие

Опишите ответ при отсутствии записей.

#### Как рассуждать и алгоритм

Нужно назвать состояние и предложить доступное действие.

#### Решение

```text
У вас пока нет записей.
[Записаться на услугу]
[В главное меню]
```

#### Проверка

Пользователь не видит техническое [] и знает, что делать.

### Задача 3. Ошибка ввода

#### Условие

Сохраните правильное название при ошибке количества.

#### Как рассуждать и алгоритм

Меняйте только проверенное поле и не очищайте весь контекст.

#### Решение

```python
def update_quantity(draft, text):
    try:
        quantity = int(text)
    except ValueError:
        return "Введите целое число"
    if quantity <= 0:
        return "Количество должно быть больше нуля"
    draft["quantity"] = quantity
    return "Проверьте заявку"
```

#### Проверка

При ошибке draft["name"] и прежние данные не исчезают.

## Самостоятельная практика

Спроектируйте три состояния записи клиента: пустой список, заполненный список, отказ сохранения. Для каждого укажите сообщение и кнопки. Проверьте путь без устных подсказок.
