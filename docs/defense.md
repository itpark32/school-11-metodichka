# Проверка программы и техническая защита

<p class="reading-time">Примерное время · Чтение: 4–6 мин · Практика: 40–70 мин</p>

!!! abstract "Фокус"
    - **Нужно знать:** ожидаемый результат, граничный случай, сквозной сценарий и ограничение.
    - **Нужно уметь:** показать работу приложения и объяснить путь данных.

## Теория

Проверка отвечает «делает ли программа обещанное», техническая защита — «понимает ли автор, как она это делает». Полезно показать один законченный сценарий и связать его с конкретными функциями.

### Порядок рассказа

Назовите пользователя и задачу. Покажите действие от начала до результата. Затем объясните модель, ответственность модулей и путь данных. Продемонстрируйте отказ, а в конце назовите ограничения и следующий полезный шаг.

### Что проверять

Обычный пример подтверждает один исход. Добавьте границу, пустой набор, неверный формат, отсутствие записи, повтор события и перезапуск. Для бота нужны два пользователя: один успешный диалог не доказывает разделение контекста.

Запишите ожидаемый результат до запуска. «Работает» без входных данных не позволяет повторить проверку. Для случайного значения проверьте диапазон, а не конкретное выпавшее число.

### Разные уровни

Чистая функция проверяется без input и Telegram. Проверка файла подтверждает восстановление типов и ID. Сквозной сценарий показывает, что UI правильно соединён с сервисом и сохранением. Успех одного уровня не заменяет остальные.

### Демонстрационные данные

Подготовьте небольшой известный каталог: обычная запись, нулевой остаток, длинное название и отсутствующий ID. Сетевую часть можно проверить искусственным ответом, явно обозначив его. Не утверждайте, что интеграция работает, если показан только макет.

### Объяснение решения

Сначала дайте прямой ответ, затем покажите место в коде. Важно объяснить, почему проверка выполняется до изменения данных, почему ID остаётся прежним и где хранится состояние. Забытый параметр библиотеки можно найти в документации; общий договор части программы нужно понимать самому.

### Полезность

Опишите наблюдаемую пользу: отчёт без ручного подсчёта, восстановление после перезапуска, отсутствие повторной записи. Не придумывайте экономию времени без измерения. Новый человек должен суметь запустить проект по README.

## Частые ошибки

Не подменяйте объяснение чтением всех файлов. Не скрывайте ограничение внешнего сервиса. Не показывайте только удачный пример. Не включайте реальные токены в демонстрацию.

## Разбор практических задач

Сначала запишите свой план и ожидаемый результат, затем сравните с разбором.

### Задача 1. Таблица проверки

#### Условие

Составьте проверки продажи.

#### Как рассуждать и алгоритм

Для каждого входа задайте ожидаемое изменение данных.

#### Решение

```text
Остаток 5, продажа 2 → успех, остаток 3.
Остаток 5, продажа 0 → отказ, остаток 5.
Остаток 5, продажа 6 → отказ, остаток 5.
Неизвестный ID → отказ, каталог прежний.
Перезапуск → сохранённый остаток восстановлен.
```

#### Проверка

Все случаи проверяются независимо на исходных данных.

### Задача 2. Граница тарифа

#### Условие

Проверьте бесплатную доставку от 5000 рублей.

#### Как рассуждать и алгоритм

Используйте значения ниже, ровно на и выше границы.

#### Решение

```python
def delivery(amount):
    return 0 if amount >= 5000 else 300
assert delivery(4999) == 300
assert delivery(5000) == 0
assert delivery(5001) == 0
```

#### Проверка

Замена >= на > должна сломать проверку 5000.

### Задача 3. Путь данных

#### Условие

Подготовьте объяснение добавления записи.

#### Как рассуждать и алгоритм

Назовите событие, проверку, изменение, сохранение и ответ.

#### Решение

```text
Команда пользователя → UI → проверенные поля → модель.
Сервис назначает ID и добавляет запись.
Хранилище записывает состояние.
UI сообщает результат и показывает обновлённый список.
При отказе укажите, какая часть не изменилась.
```

#### Проверка

Сверьте каждую строку с конкретным кодом своего проекта.
