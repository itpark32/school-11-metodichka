# Git и история рабочего проекта

## Теория

Git хранит историю изменений проекта. Коммит — зафиксированный набор изменений с сообщением. GitHub — удалённый сервис, который может хранить репозиторий; это не то же самое, что Git на компьютере.

### Три состояния

Рабочие файлы — то, что редактируется сейчас. Индекс содержит изменения для следующего коммита. Коммит сохраняет снимок выбранного состояния. `git status` показывает различия, `git diff` — непроиндексированные изменения, `git diff --cached` — подготовленные к коммиту.

### Маленькие законченные изменения

Один коммит должен объясняться одним предложением: «Добавлена проверка количества заказа». Перед коммитом запустите сценарий и посмотрите diff. Не включайте в него случайные временные файлы, виртуальное окружение и реальные базы.

Ветка позволяет работать над отдельной задачей. При слиянии может возникнуть конфликт: Git не может самостоятельно выбрать правильный результат. Прочитайте обе версии, соберите нужный вариант и проверьте поведение. Удалить маркеры конфликта недостаточно.

### Конфигурация и секреты

В `.gitignore` обычно добавляют `.venv/`, `.env`, `__pycache__/` и локальные данные. Файл `.env.example` содержит названия переменных без действующих ключей. Игнорирование не удаляет уже отслеживаемый файл и не очищает историю. Если секрет опубликован, его отзывают у провайдера.

В совместной работе заранее договоритесь о файлах и сценариях. Разделение по слоям помогает двум людям менять разные части, но не отменяет необходимости согласовать договор функций.

## Частые ошибки

`git add .` может захватить лишнее. `push` отправляет коммиты, а не текущие несохранённые изменения. Не используйте force push для обычной синхронизации совместной ветки.

## Разбор практических задач

Сначала составьте свой план решения. Затем сравните его с разбором и проверьте результат.

### Задача 1. Проверка изменений

#### Условие

Перед коммитом посмотрите, какие файлы изменены и что именно в services.py поменялось.

#### Как рассуждать и алгоритм

Сначала общий статус, затем конкретный diff. Команды выполняйте в своём учебном репозитории.

#### Решение

```bash
git status --short
git diff -- services.py
```

#### Проверка

В diff должны быть только ожидаемые изменения. Если services.py не изменён, diff пуст.

### Задача 2. Коммит одной задачи

#### Условие

Подготовьте только исправление services.py, затем сохраните его.

#### Как рассуждать и алгоритм

Добавьте конкретный файл, проверьте индекс и только после этого создайте коммит.

#### Решение

```bash
git add services.py
git diff --cached
git commit -m "Проверка количества товара перед продажей"
```

#### Проверка

`git show --stat HEAD` показывает services.py. В коммит не должны попасть .env и локальные данные.

### Задача 3. Рабочая ветка

#### Условие

Начните отдельную задачу по отчёту и проверьте текущую ветку.

#### Как рассуждать и алгоритм

Создайте ветку с понятным именем. Это не отправляет код на сервер.

#### Решение

```bash
git switch -c feature/sales-report
git branch --show-current
```

#### Проверка

Вывод feature/sales-report. Если ветка уже существует, переключитесь через git switch feature/sales-report.

## Самостоятельная практика

В учебной ветке добавьте проверку пустого отчёта. До коммита покажите diff, после — историю из трёх последних коммитов. Составьте README с командами запуска и примером конфигурации.
