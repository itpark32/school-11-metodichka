# 16. Git и история проекта

<p class="reading-time">Чтение: 6 минут</p>

Git сохраняет понятные этапы работы над кодом. Благодаря истории можно сравнить версии, вернуться к рабочему состоянию и безопаснее делать большой проект.

!!! abstract "Фокус"
    - **Нужно знать:** репозиторий, изменение, коммит, `status`, `add`, `commit`, `push`.
    - **Часто в работе:** `.gitignore`, небольшие коммиты и понятные сообщения.
    - **Достаточно узнавать:** ветки, слияния и разрешение конфликтов.

## Обычный цикл

```bash
git status
git add main.py product.py
git commit -m "Add product creation"
git push
```

`git status` показывает изменения. `git add` выбирает файлы для следующего коммита. `git commit` сохраняет снимок локально, а `git push` отправляет новые коммиты на GitHub.

## Хороший коммит

Коммит должен содержать одно законченное изменение. Сообщение объясняет результат:

- `Add search by product name` — понятно;
- `changes` или `fix` — непонятно;
- добавление поиска и полная переделка меню одним коммитом — слишком большой шаг.

Перед коммитом запустите программу и посмотрите diff. Не добавляйте пароли, временные файлы, папки окружения и `__pycache__`.

## История как маршрут проекта

Большой магазин создавался поэтапно: модель, CRUD, ввод, сохранение, поиск, сортировка и отдельные меню. Git позволяет фиксировать такие этапы, чтобы каждая версия оставалась рабочей.

!!! warning "Коммит не заменяет резервную копию удаленного репозитория"
    Пока коммиты находятся только на компьютере, потеря папки может уничтожить и историю. Регулярно отправляйте работу в свой удаленный репозиторий.

## Мини-практика

Создайте репозиторий для маленькой игры. Сделайте три отдельных коммита: базовый запуск, основная логика, проверка ошибок. По истории должно быть понятно, как рос проект.

## Проверьте себя

1. Чем `git add` отличается от `git commit`?
2. Что делает `git push`?
3. Почему маленькие коммиты удобнее одного огромного?
4. Какие файлы не стоит добавлять в репозиторий?
