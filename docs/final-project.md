# Разработка приложения: от требований до рабочего сценария

<p class="reading-time">Примерное время · Чтение: 4–6 мин · Практика: 120–210 мин</p>

!!! abstract "Фокус"
    - **Нужно знать:** минимальная версия, модель, договор функции, вертикальный срез и проверка результата.
    - **Нужно уметь:** спланировать проект и расширять его без смешивания интерфейса и данных.

## Теория

Большая программа развивается через законченные сценарии. Магазин, журнал заявок и бот записи имеют общую основу: модель, операции, хранение и UI. Начинайте с понятного результата, а не с десятков файлов с pass.

### Порядок разработки

1. Пользователь и задача: что он хочет получить.
2. Минимальные сценарии и ограничения.
3. Модель данных, поля, ID и допустимые значения.
4. Договоры функций: вход, выход, изменение, отказ.
5. Чистые операции без интерфейса.
6. Один вертикальный путь от команды до результата.
7. Сохранение и проверка повторного запуска.
8. Следующие сценарии и приёмка.

### Модель и бизнес-операция

CRUD описывает общие изменения, но пользовательская операция может включать несколько правил. Продажа проверяет количество и остаток; запись — занятость слота; закрытие заявки — допустимый статус. Эти правила находятся в сервисе, а UI только передаёт запрос и показывает ответ.

### Минимальная версия

Для каталога достаточно добавления, списка, поиска и сохранения. Затем можно добавлять покупку, роли и экспорт. Для бота начните с одного многошагового пути и отмены, прежде чем подключать все внешние API.

### Работа одному и в группе

В соло ведите небольшой список задач и сохраняйте рабочие шаги в Git. В группе заранее согласуйте файлы и договоры функций: кто пишет модель, кто операции, кто UI. Ветка не решает конфликт смысла, если два автора по-разному понимают результат одной функции.

### Проверяйте отказы вместе с успехом

Если ошибка в последнем шаге, не оставляйте данные частично изменёнными. Для файлового приложения можно подготовить новую коллекцию и подтвердить замену после проверки. При многопользовательской одновременной записи требуется более надёжное хранилище — это отдельное развитие проекта.

### Что считать готовностью

Готовый сценарий запускается по инструкции, выполняет задачу, объясняет отказ и сохраняет нужные данные. Скриншот интерфейса или перечень папок не доказывают завершённость. На защите покажите путь одного события и конкретную функцию каждого слоя.

## Частые ошибки

Не называйте пустой каркас готовым проектом. Не начинайте все сценарии одновременно. Не делайте UI владельцем всех правил. Не объединяйте изменения без проверки договоров.

## Разбор практических задач

Сначала запишите свой план и ожидаемый результат, затем сравните с разбором.

### Задача 1. Проверяемый сценарий

#### Условие

Опишите добавление услуги от ввода до повторного запуска.

#### Как рассуждать и алгоритм

Зафиксируйте наблюдаемый результат и ошибку, при которой запись не создаётся.

#### Решение

```text
Ввод названия и цены → проверка → новый ID → добавление → сохранение.
После успеха: услуга видна в списке и после перезапуска.
При отрицательной цене: пояснение, каталог не изменяется.
При ошибке записи: нет ложного сообщения «Сохранено».
```

#### Проверка

Каждую строку можно воспроизвести на учебных данных.

### Задача 2. Изолированный сервис

#### Условие

Сервис должен принимать функцию проверки доступности.

#### Как рассуждать и алгоритм

Передача зависимости позволяет проверять правило без настоящего файла.

#### Решение

```python
def can_book(slot, is_available):
    return bool(slot) and is_available(slot)
print(can_book("10:00", lambda slot: slot != "10:00"))
```

#### Проверка

Занятое время → False. Пустая строка не вызывает внешнюю проверку.

### Задача 3. Смена статуса

#### Условие

Согласуйте переход new → in_progress → done.

#### Как рассуждать и алгоритм

Храните разрешённые переходы как данные, до присваивания проверяйте событие.

#### Решение

```python
def change_status(ticket, target):
    allowed = {"new": {"in_progress"}, "in_progress": {"done"}, "done": set()}
    if target not in allowed.get(ticket["status"], set()):
        return False
    ticket["status"] = target
    return True
```

#### Проверка

Переход new→done отклоняется без изменения. Повторное завершение тоже отклоняется.
